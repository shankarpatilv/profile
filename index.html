Outages and releases should be boring.

Cloud providers split each region into separate data centers called availability zones. The app runs copies in several of them, on AWS or Azure, behind a load balancer that only sends visitors to copies that pass a health check.

If a whole zone fails, the other copies keep serving while new ones start automatically.

Releases roll out one copy at a time, so a working version is always online. The whole setup is written as code, so it can be rebuilt on either cloud instead of clicked together by hand.

Slow tasks like sending verification emails moved to background jobs, which cut response times by 35%.

What it costs: spare capacity you pay for and hope never to use, and skipping shortcuts that only work on one cloud.

Many workers, one rule: never lose an event.

Think of every click, order or log line as an event. Events arrive in order through Kafka, a queue built for heavy streams, and a pool of workers handles them in parallel to keep up.

The catch is that parallel workers finish out of order. If the system marks “everything up to 500 is done” while event 497 is still running, and that worker crashes, event 497 is gone and nobody notices.

My fix keeps a small ledger for each stream and only moves the “done” marker forward once everything before it has finished. And when the database slows down, workers simply take less, so the slowdown travels back to the source instead of piling up in memory.

What it costs: after a crash, a few events can be processed twice. A repeat is easy to handle. A gap is not.

Results land in two databases on purpose: one that is quick at finding a single record, and one that is quick at adding up millions. That split made analytics queries 10 to 100 times faster.

You already have the stories. They’re just scattered.

Behavioral questions like “tell me about a hard bug” need real examples. Most people have them, buried in old notes, tickets and memory, and dig them up again before every interview.

With InterviewKit, you write short notes about past projects once. It breaks them into small pieces and stores them so they can be searched by meaning, not just by keywords.

Give it a job description and a company’s values, and it drafts the questions you’re likely to get. For each one, it pulls the closest pieces of your notes and writes a STAR answer (situation, task, action, result), naming the note it came from.

What it costs: when none of your notes fit a question, it says so instead of making up a story. A confident fake answer is worse than none.

Each step is an explicit, testable workflow rather than a free-roaming AI agent, and your private notes stay out of version control.

With data this sensitive, security can’t be added at the end.

Built with three classmates at Northeastern, ChildGuard gives families free learning and health resources, lets volunteers and donors sign up to help, and lets anyone report a child safety concern without giving their name.

My part focused on keeping it secure and fast. Every request passes a series of checks before it can touch any data.

Logins use signed tokens, and every account has a role: people see only their own activity, and only admins can review safety reports. Every input is cleaned, so a hidden script can’t slip into a report, and strict browser security headers block common attacks.

On the data side, better indexes and leaner database queries made the app respond faster.

What it costs: a few more checks on every request. For safety reports, that’s the right trade.

Saving a record shouldn’t wait for search to catch up.

Every record also has to show up in search. Updating the search index takes time, and the service used to make every save wait for it before answering.

Now the save goes straight to storage, and a separate background worker updates search a moment later. Saves got 60% faster.

Repeat reads are cheap too. If a client already has the latest version of a record, the server just replies “nothing changed” instead of fetching it again.

Every request needs a valid login token and has to match a strict format before it is accepted, so bad data never gets in.

What it costs: search can trail a fresh save by a moment, which is fine for this kind of data.
